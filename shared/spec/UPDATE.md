# BrainFuel Update Contract

> Online updates are the release vehicle: every platform must be able to
> check, download, verify and install a new version without the user
> hunting for download pages. The **behavior** (triggers, UX, strings,
> failure handling) is identical on all platforms; the **transport and
> install mechanism** is native to each platform, like every other part
> of the BrainFuel architecture. This is the family contract — taskly's
> `shared/spec/UPDATE.md` with the product substituted.

## Behavior contract (all platforms)

- **Triggers**: one silent check shortly after launch (throttled: at most
  once per 4 hours, persisted as the updater-state key `last-update-check`,
  unix epoch seconds, host-owned via `get-setting`/`set-setting`), plus a
  manual `检查软件更新 / Check for Updates` entry in the tray/card menu and
  the Settings ▸ Software tab that bypasses the throttle.
- **Silent mode**: network failure / rate limit → silently ignore (never
  nag). Manual mode reports every outcome.
- **Newer version found** (semver compare, downgrades ignored) → dialog
  with the new version: `立即更新 / Update` (download + install) or
  `取消 / Cancel`. Up-to-date → `已是最新版本 / Up to date`.
- **Download**: performed by the backend over the `check-updates` /
  `start-download` / `update-state` RPCs (rivet/distribution family
  pattern — Ed25519 manifest verify and sha256 artifact verify live in
  the backend; hosts never implement crypto). Hosts poll `update-state`
  (phase: idle | checking | downloading | downloaded | error) and show
  progress. macOS is the family exception: its host fetches and verifies
  the same signed wrapper itself (CryptoKit) so the swap can run entirely
  in-process.
- **Install failure** → non-crashing error with the platform message;
  the running version keeps working (same rule as notifications).
- i18n keys are shared (`shared/i18n`): `MenuCheckUpdates`, `BtnCheckUpdates`,
  `UpdateChecking`, `UpdateUpToDate`, `UpdateAvailableTitle`,
  `UpdateAvailableBody`, `UpdateRestart`, `UpdateCheckFailed`,
  `UpdateDownloading`, `UpdateDownloadPercent`, `UpdateDownloaded`,
  `UpdateQuitAndInstall`, `UpdateReadyBody`, `UpdateInstallFailed`,
  `UpdateInstallHint`, `UpdateOpenFolder`, `UpdateNotInstalled`,
  `UpdateMsiInstalled`, `UpdateOpenReleases`, `UpdateOpenDownloads`.

## Platform mechanisms

The release pipeline signs and uploads `update-manifest.json` (the
self-contained signed wrapper, below) for every release, so the feed
exists on all platforms from day one.

| Platform | Feed | Install | Integrity | Status |
|---|---|---|---|---|
| macOS Apple silicon | feed `macos`/`arm64` zip entry | zip → sha256 → ditto → atomic swap in place (`.old` copy kept until relaunch); the DMG is the human installer, not a feed artifact | Ed25519 wrapper signature (CryptoKit, `UpdateService.swift`) + artifact sha256 | wired since 0.1.0 |
| macOS Intel | feed `macos`/`x64` zip entry | same swap flow on the x64 build (hosts match their compile-time architecture) | same | wired since 0.1.0 |
| Windows x64 | feed `windows`/`x64` zip entry | zip → handoff `update-install.cmd`: wait for app exit → `tar -xf` extract → swap install dir in place → relaunch; failure marker (`update-failed.txt`) reported on next launch. MSI installs under Program Files get guidance to the releases page instead of a swap they cannot make | Ed25519 wrapper signature (backend, libcrypto) + artifact sha256 | wired since 0.1.0 |
| Linux x64 | feed `linux`/`x64` tar.gz entry | backend downloads the tar.gz → dialog offers "open folder"; install is a manual extract over the current folder (tarball installs have no fixed prefix to self-swap) | Ed25519 wrapper signature (backend, libcrypto) + artifact sha256 | wired since 0.1.0 (download in-app, install manual) |

## `update-manifest.json`

Generated by `scripts/make-update-manifest.sh` from the release
artifacts and uploaded as a single release asset. It is the family
signed-wrapper format (`rivet/distribution`): the inner manifest travels
base64-encoded inside a JSON envelope, so the Ed25519 signature covers
the exact bytes every client verifies.

```json
{
  "schema": 1,
  "payload": "<base64 of the inner manifest JSON>",
  "signature": { "algorithm": "ed25519", "key_id": "brainfuel-2026-10",
                 "value": "<base64, 64 bytes>" }
}
```

Inner manifest (decoded `payload`) — rivet's manifest schema:

```json
{
  "schema": 1,
  "application_id": "site.jrtx.brainfuel",
  "version": "0.1.0",
  "build": 1,
  "channel": "stable",
  "published_at": "2026-10-10T12:00:00Z",
  "minimum_version": "0.0.0",
  "previous_version": null,
  "rollback_allowed": true,
  "rollout": 100,
  "artifacts": [
    { "platform": "macos", "architecture": "arm64",
      "url": "https://…/brainfuel-0.1.0-macos-arm64.zip",
      "sha256": "<hex>", "size": 12345678, "installer": "zip", "arguments": [] },
    { "platform": "macos", "architecture": "x64", "…": "…" },
    { "platform": "windows", "architecture": "x64", "…": "…" },
    { "platform": "linux", "architecture": "x64", "…": "…" }
  ]
}
```

- `version` must equal the root `VERSION` file (release preflight checks
  it, along with `rivet.rktd` and the updater module's embedded identity).
- The four **portable** artifacts are the feed; dmg/msi are human
  installers and stay out of it.
- Clients fetch
  `https://github.com/turinglambdaai/brainfuel/releases/latest/download/update-manifest.json`
  (the moving "latest" location; redirect-following is mandatory —
  release assets 302 to the CDN, rivet#153). Artifact URLs inside the
  manifest are pinned to the concrete tag.
- A sticky per-install rollout bucket (updater-state key `rollout-bucket`,
  integer 0–99) gates staged rollouts against the manifest's `rollout`
  percentage.

## Ed25519 signature

- Key type: Ed25519. Private key lives ONLY in the GitHub secret
  `UPDATE_ED25519_PRIVATE_KEY_B64` (OneAsymmetricKey DER, base64 — the
  same secret the windows/linux release legs already consume) and in the
  release manager's local backup (`.keys/`, gitignored) — never in the
  repository.
- Generate / inspect: `scripts/update-keys.sh` (openssl, one-time) — it
  prints every derived form: SPKI DER base64 (backend), raw 32 bytes
  base64 (macOS host), private DER base64 (the CI secret).
- Sign: `make-update-manifest.sh` accepts PEM or DER key files (PEM is
  converted with `openssl pkey -outform DER`) and the wrapper is signed
  by `rivet/distribution`'s `write-signed-manifest` (which also validates
  the manifest against the schema before signing).
- Public key: embedded twice, same keypair — raw 32 bytes base64 in the
  macOS host (`UpdateService.publicKeyBase64`) and SPKI DER base64 in the
  backend updater (`racket/brainfuel/updater.rkt`). `key_id` is
  `brainfuel-2026-10`; clients pin it. Rotate = ship a build that trusts
  the next key before releases stop being signed with the old one.
- Verification: wrapper → schema 1 → key id → Ed25519 over the exact
  payload bytes; then size + sha256 of the downloaded artifact against
  the signed manifest. Any mismatch aborts the update silently in
  silent mode, with an error in manual mode.

## Rollout rules

- Downgrades are never auto-installed; semver compare is numeric per
  segment.
- The updater must never delete or touch the backend data dir
  (`settings.json`, credentials, usage history) — it swaps application
  bundles/prefixes only.
- A failed swap must leave the previous install runnable (macOS keeps a
  `.old` copy until the next successful launch; Windows restores the
  renamed directory and writes a failure marker the next launch
  reports).
